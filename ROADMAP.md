# gtv — roadmap

CLI над `./gradlew test`: сгруппированный по `@DisplayName`/`@Nested` вывод для человека
и компактный, экономный по токенам — для кодинг-агента.

Стек: Go 1.22, без внешних зависимостей. Источник данных — Gradle init-script,
стримящий NDJSON (`internal/gradlescript/listener.gradle`), не парсинг консоли.

---

## Сделано

### M0 — источник данных (закрыт)

`internal/gradlescript/listener.gradle`, подключается через `-I`, пишет NDJSON в
файл из `-Dgtv.out=`. Проверен на `UserServiceTest` в реальном multiproject.

### M1 — ридер + agent-рендер (закрыт)

```
cmd/gtv/main.go              CLI, exit-коды, разбор причин падения сборки
internal/event/              NDJSON-модель
internal/model/              дерево suite/test, схлопывание scaffolding
internal/render/             agent-рендер, фильтр стека
internal/runner/             JAVA_HOME, поиск wrapper'а, spawn, поллинг-tail
```

`go test ./...` зелёный. Вызов сейчас: `gtv :app:service:test --tests "..."`.

### Ревью M1 (закрыто)

Разобраны замечания `CODE_REVIEW.md`. Исправлено:

- перезапуск тестов форсируется в init-скрипте (`upToDateWhen{false}` + `cacheIf{false}`),
  а не флагом `--rerun`: тот применялся только к названной задаче, из-за чего
  `gtv :module:check` печатал ложный `NOTESTS` при успешной сборке
- ключ узла — `task + TestDescriptorInternal.getId()` вместо цепочки имён:
  одноимённые dynamic-тесты сливались в один узел и терялись из счётчиков
- память ограничена: хвост Gradle-лога (256 КБ, с пометкой об отбрасывании),
  окно вывода теста (200 чанков по 4 КБ)
- ошибки чтения потока и нечитаемые строки больше не глотаются
- удалён мёртвый `DecodeAll`, исправлен неверный комментарий `Leaves`,
  убрана недостижимая ветка в `wrapperCommand`

Сознательно не менялось: аллокации в `Node.Path()` (глубина 3–5, вызов на упавший тест).

### M2 — human-рендер (закрыт)

```
internal/render/human.go     дерево, ветви ├─ │ └─, цвет, сворачивание параметризованных групп
internal/render/live.go      live-прогресс через runner.Config.OnEvent
```

- [x] `internal/render/human.go`: дерево по `model.Tree.Suites()`, ветви `├─ │ └─`,
      счётчики и длительность на каждой суите
- [x] цвет: зелёный SUCCESS, красный FAILURE, жёлтый SKIPPED; отключается при
      `NO_COLOR`, `TERM=dumb` и когда stdout не tty
- [x] выбор рендера в `main.go`: tty → human, иначе agent; флаги `--agent` / `--human`
      перебивают. `CLAUDE_CODE`/`CI` в env форсируют agent-рендер даже на tty
- [x] живой прогресс через `runner.Config.OnEvent`: перерисовка последних N строк
      (ANSI `\r\x1b[K`, без alt-screen), финальный кадр — полное дерево
- [x] параметризованные тесты: сворачивать группу в одну строку `N/M ok`, разворачивать
      только упавшие инвокации
- [x] тесты рендера на зафиксированном NDJSON-фикстуре (`human_test.go`)

Найдено по ходу: контейнер `@ParameterizedTest`-метода и `@Nested`-класс с одним
тестом структурно неотличимы по "все дети — листья" — у обоих может быть один
ребёнок-тест. Разошлись по `TestDescriptor.className`: у `@Nested` он свой
(новый класс), у параметризованного контейнера — тот же, что у родителя.
`paramGroup()` в `human.go` проверяет именно это, не количество детей.

`Node` получил агрегатные счётчики (`Total/Ok/Failed/Skipped`) из `suiteEnd`
(`total/ok/failed/skipped` в NDJSON и раньше были, но `Tree.Apply` их не
сохранял) — нужны, чтобы не пересчитывать поддерево рекурсией на каждой суите.

Live-рендер держит свой собственный `model.Tree` и складывает в него те же
события, что видит `runner.Execute`: `OnEvent` отдаёт только `event.Event`, не
ссылку на финальное дерево раннера.

**DoD**: `gtv :app:service:test --tests "*.UserServiceTest"`
печатает дерево `UserQueryService` → 5 `@Nested`-групп → тесты, с цветом.

## M3 — резолв цели (важнее human-рендера для агента)

Цель: `gtv UserServiceTest` вместо полного пути таски.

```
internal/target/target.go    аргумент → (gradle task path, --tests паттерн), кеш индекса
```

- [x] `internal/target`: аргумент → (gradle task path, `--tests` паттерн)
  - [x] аргумент это `:a:b:test` → отдать как есть
  - [x] путь к файлу `.kt`/`.java` → FQN из `package` + имени файла
  - [x] простое имя класса или FQN → поиск файла под `**/src/test/**`
  - [x] от найденного файла вверх до ближайшего каталога с `build.gradle(.kts)`,
        относительный путь от корня → `:a:b`; таска = `:a:b:test`
  - [x] `Class.methodName` или `Class::method` → `--tests "FQN.methodName"`
- [x] кеш индекса в `~/.cache/gtv/<hash пути к корню>.json` (через `os.UserCacheDir()`,
      на Linux то же самое, но переносимо на Windows/macOS), инвалидация по mtime
      каталогов `src/test`; флаг `--reindex`
- [x] несколько совпадений → перечислить кандидатов и выйти с кодом 2, не угадывать
- [x] тесты на подставном дереве каталогов (`t.TempDir()`) — `internal/target/target_test.go`

Инвалидация кеша не хранит mtime только верхнего `src/test`, а всех каталогов под ним:
добавление файла всегда меняет mtime родительского каталога (создание/удаление/переименование
записи в директории), так что новый каталог тоже ловится — через mtime уже отслеживаемого
родителя, без обхода дерева заново на каждый запуск.

`Resolve` сперва пробует весь аргумент как класс (путь, FQN или простое имя); только если
это ничего не нашло (`ErrNotFound`, не `ErrAmbiguous`) — пробует разбить по первому `.`/`::`
на класс+метод. Так `UserServiceTest.should pass` не путается с `com.example.Foo`
(точки в FQN), а найденная неоднозначность не заслоняется попыткой распарсить как метод.

`gtv UserServiceTest` и `gtv UserServiceTest.should pass` собраны и
покрыты тестами на фиктивном дереве каталогов; `go build`, `go vet`, `go test ./...` зелёные.
Не проверено на реальном multiproject-репозитории — DoD ниже нужно подтвердить живым
прогоном.

**DoD**: `gtv UserServiceTest` и `gtv UserServiceTest.should pass` работают
из любого каталога внутри репозитория.

## M4 — режимы без прогона (закрыт)

```
internal/lastresults/lastresults.go   парсер JUnit XML -> тот же model.Tree
internal/render/json.go               JSON-рендер того же дерева
internal/watch/watch.go               поллинг mtime, перезапуск при изменении
```

- [x] `--last`: читать `*/build/test-results/**/TEST-*.xml` вместо запуска Gradle;
      парсер на `encoding/xml`. Учесть: в XML нет `@DisplayName` класса, вложенные
      классы видны как `Outer$Nested` в `classname` — иерархию восстанавливать по `$`
- [x] `--json`: машинный вывод (то же дерево, без ANSI) для агентов, которым нужен разбор
- [x] `--watch`: перезапуск при изменении `src/**` (поллинг mtime, без внешних зависимостей)

`--last` не запускает Gradle вообще, поэтому строит `model.Tree` не из потока событий,
а проигрывая по нему те же `event.Event` (`suiteStart/suiteEnd/testStart/testEnd`),
которые сгенерировал бы живой прогон.
Так `Total/Ok/Failed/Skipped` и вся логика рендера (`paramGroup`, `Suites()`, `Leaves()`)
остаются той же, без дублирования под второй источник данных.

Иерархия вложенных классов восстанавливается через `classname="Outer$Nested"` —
разбивкой по `$` строится trie, затем проигрывается глубина-в-глубину.
У XML нет абсолютных таймстампов, только `time` каждого testcase, поэтому `Start/End`
узлов — не настоящее время суток, а бегущие часы: каждый лист сдвигает их на свою
длительность, у сьюта `Start/End` — где часы были на входе и на выходе.
Итоговая длительность прогона получается суммой длительностей тестов, а не wall time
(который по одному отчёту не восстановить).

Резолв цели (`target.Resolve`) переиспользуется как есть: `--last FooTest` находит
модуль и таск так же, как обычный запуск, а найденный таск разворачивается в путь
`build/test-results/<task>` через `lastresults.Dir`.
Фильтр по классу/методу срезает лишние XML-файлы по имени `testsuite`, а не по
Gradle-паттерну `--tests` — XML целиком уже на диске, фильтровать внутри класса
по методу незачем.

`--json` — это не режим human/agent, а третий вариант рендера того же `model.Tree`:
дерево сьютов и тестов с полями `status/duration_ms/total/ok/failed/skipped`,
у упавших тестов — `failures[]` с сообщением, классом, expected/actual и обрезанным
по `--max-fail`-совместимому `MaxFrames` стеком.
Разделяет опции с agent-рендером (`render.Options`), поэтому `--test-output`
и `--max-fail` действуют одинаково на оба.

`--watch` не привязан к `src/**` конкретного модуля — следит за всем корнем Gradle-репо,
пропуская `.git/.gradle/.idea/build/out/node_modules` (тот же список каталогов,
что и в `target.buildIndex`).
Проще держать один поллер на весь репозиторий, чем резолвить цель заранее только
ради вычисления каталога слежения — обычный `gradle test` и так пересобирает только
изменившиеся модули за счёт своего up-to-date кэша (кроме тестовой таски, которую
форсирует init-script).

      (`GOOS=... go build`), `-ldflags "-s -w -X main.version=..."`, версия из

- [x] README с примерами вывода
- [ ] опционально: `--install-hook` для Claude Code, переписывающий `./gradlew ... test` в `gtv`

Добавлен `--version` (значение из `-X main.version=`), иначе `-ldflags` в
`build.sh` нечего было бы подставлять.
Три платформы собираются чисто (`./build.sh`): ELF/Mach-O/PE подтверждены
через `file`, `--version` печатает встроенную версию.

вызов wrapper'а через `cmd /c`, поведение `--watch`/`--last` на путях с `\`.

## M6 — счётчик сэкономленных токенов (закрыт)

Цель: после прогона видно, сколько токенов `gtv` сэкономил агенту vs сырой вывод gradle.

```
internal/stats/stats.go     Record/Load/Format, ~/.cache/gtv/stats.json
```

- [x] базовая метрика: длина agent-рендера (символы, оценка токенов `len/4`) vs
      полный объём stdout+stderr Gradle за тот же прогон
- [x] накопление между прогонами: `~/.cache/gtv/stats.json` — сумма baseline/actual
      за всё время + по проекту (hash пути к корню, как в M3 индексе)
- [x] `gtv --stats` / `gtv stats`: сколько сэкономлено всего, за сессию (процесс),
      средний % на прогон, разбивка по проектам
- [x] решение по baseline: считать **реальный** вывод Gradle того же запуска
      (`tailWriter.Total` считает все байты, даже отброшенные из хвоста 256 КБ).
      Второй прогон не нужен; оценка по NDJSON отвергнута как неточная на
      многомодульных сборках. `--last` статистику не пишет (нет Gradle-консоли).

После каждого успешного прогона с тестами на stderr уходит строка
`gtv: saved ~N tokens (P%) this run`; stdout отчёта не трогается.

**DoD**: `gtv --stats` после нескольких прогонов печатает суммарную экономию токенов.

## Известные факты (проверены, не переоткрывать)

- `TestDescriptor.getDisplayName()` есть в Gradle 9.2 и отдаёт `@DisplayName` класса,
  `@Nested`-класса и имя параметризованной инвокации (`page=1 size=50 -> expectedLimit=50`).
- Стектрейс Gradle уже чистит: 6–8 строк, первый фрейм — код теста. Свой фильтр
  в `internal/render/failure.go` добивает остатки (`java.`, `org.junit`, …).
- Kotlin-имена методов содержат пробелы — regex фреймов не может рассчитывать
  на идентификатор перед скобкой.
- `TestFailureDetails.getExpected()/getActual()` заполняются **только** для opentest4j
  (JUnit `assertEquals`). AssertJ кидает голый `AssertionError` — там полезен только `msg`.
- `@Disabled` и провалившийся assumption оба приходят как `SKIPPED`. Причина есть только
  у assumption, через `TestResult.getAssumptionFailure()`. Текст `@Disabled("…")` Gradle
  не отдаёт вовсе.
- При пустом `--tests`-фильтре Gradle всё равно шлёт scaffolding-сьюты, поэтому пустой
  прогон определяется по числу тестов, а не событий.
- Ошибка компиляции даёт в секции `What went wrong` только `See log for more details`;
  сама диагностика идёт выше строками `e: file://…`.
- Без форсирования повторный прогон UP-TO-DATE (или FROM-CACHE, `org.gradle.caching=true`)
  и не шлёт ни одного события.
- Configuration cache в проверенном multiproject был выключен; совместимость init-script с
  `--configuration-cache` **не проверялась**.
- `TestDescriptorInternal.getId()` достаётся из init-скрипта duck typing'ом без
  импорта internal-класса и даёт `1.4`, `1.5`, … — уникально **в пределах задачи**,
  поэтому ключ узла обязан включать task path.
- `--rerun` — task option: на агрегирующей задаче (`check`, `build`) перезапускает
  только её саму, оставляя `test` UP-TO-DATE. Воспроизведено.

## Открытые вопросы

- Параллельные форки (`maxParallelForks > 1`): события классов перемешаются.
  Дерево это переживёт, live-рендер (`internal/render/live.go`) — нет, у него
  плоский хвост последних завершённых тестов без группировки по суите.
- Многомодульный прогон (`gtv test` по всему репо): сейчас заголовок склеивает
  все таски в строку. Нужна группировка вывода по таскам.
- Размер NDJSON на большом прогоне (стектрейсы целиком). Пока файл во временном
  каталоге и удаляется — но стоит померить.
